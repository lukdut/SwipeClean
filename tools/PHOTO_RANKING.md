# Персональная сортировка фотографий

## Как работает

1. Ручной анализ вычисляет прежние признаки качества и визуальный вектор SigLIP 2.
   Обрабатываются также просмотренные фото, чтобы дополнить историю решений.
2. При свайпе сохраняются решение, идентификатор версии фото, возраст на момент
   решения (если известна дата съёмки), вектор и версия модели. Если анализ ещё
   не выполнен, решение ожидает признаков.
3. Сравниваем фото с близкими примерами из истории. Удаления повышают приоритет,
   оставленные фото снижают. Результат складывается с технической оценкой;
   настройка «Похожие фотографии» регулирует вклад истории.
4. Текущая и следующая карточки сохраняют положение при фоновых обновлениях.
   Выбор другого порядка/приоритета применяет сортировку сразу.

Категории изображений не перечисляются. Текстовых запросов к модели, передачи фото на сервер
и автоматического удаления нет. Сеть используется для скачивания модели и проверки обновлений. Без подходящих примеров работает
прежняя оценка качества. Модель определяет визуальное сходство; она не знает,
нужен ли пользователю конкретный документ или закончился ли срок его полезности.
База с признаками и историей исключена из облачной резервной копии Android и
переноса между устройствами; идентификаторы MediaStore привязаны к устройству.

## История и согласованность

- `KEPT` и подтверждённое `DELETED` имеют вес 1; предварительное `TRASH` — 0.5.
- Восстановление отменяет `TRASH`. Повторное решение заменяет пример с тем же
  ключом, а не накапливает дополнительные голоса. Само фото исключается из соседей.
- Перед запросом окончательного удаления дополняем недостающие признаки, если модель
  уже установлена. Удаление не запускает скачивание модели. Подготовку можно отменить.
  Ошибка модели не блокирует удаление.
- Отмена системного запроса оставляет фото в корзине и не создаёт `DELETED`.
  Исчезновение файла вне приложения не считается подтверждённым удалением.
- Признаки и решение живут в `photo_feedback` без внешнего ключа к кэшу/файлу.
- Очистка истории не сбрасывает очередь/корзину. Незавершённый анализ не может
  воссоздать очищенный пример: он только обновляет существующие записи.
- Сброс прогресса отменяет отметки корзины, сохраняет историю оставленных и
  окончательно удалённых фото. Для полного сброса рекомендаций есть отдельная кнопка.
- Миграция Room 2 → 3 сохраняет прежние результаты и создаёт ожидающие признаки
  примеры для старых решений, у которых в кэше есть идентификатор версии файла.

## Модель и ресурсы

Стартовая модель — квантованный визуальный энкодер `google/siglip2-base-patch16-224`,
исполняемый ONNX Runtime 1.30.0 на CPU. Файл занимает 94 553 333 байта (около 90 МиБ).
ONNX-файл исключён из Git и APK/AAB; обычная сборка не требует его скачивания.
В `assets/models` остаются небольшой JSON-манифест, NOTICE и лицензия.

### Загрузка на устройстве

- Первый анализ запускается кнопкой «Скачать модель и анализировать». До нажатия
  показан размер загрузки; сам просмотр галереи не требует модели или интернета.
- Загрузка идёт в существующем foreground service с типом `dataSync`, прогрессом
  в настройках и уведомлении. После подготовки модели сервис переходит к анализу
  (`mediaProcessing` на Android 15+, `dataSync` на более ранних версиях).
- Файл сохраняется в `noBackupFilesDir/embedding-models`; Android не очищает его как
  временный кэш и не переносит в резервную копию. Очистка данных или удаление приложения
  удаляет и модель.
- HTTPS-загрузка ограничена заявленным размером; редиректы разрешены только на HTTPS.
  Проверяются точный размер и SHA-256, имена и формы тензоров, затем пробное вычисление.
  Только после этих проверок атомарно записывается выбранная версия.
- При отмене или ошибке частичный файл удаляется. Повторная попытка скачивает его заново.
  Подключение и чтение имеют тайм-аут 15 секунд; остановка при зависшей сети может
  занять это время. При закрытии процесса загрузка сама не возобновляется.
- Установленная модель используется офлайн. Сеть не проверяется при обычном запуске
  анализа, удалении фотографий или открытии приложения.
- Хранятся текущая и одна предыдущая модель. При повреждении текущей или ошибке
  её проверки после перезапуска приложение восстанавливает предыдущую рабочую версию.

### Обновление модели без новой версии приложения

Кнопка «Проверить обновление модели» читает:

```text
https://raw.githubusercontent.com/lukdut/SwipeClean/master/app/src/main/assets/models/embedding-model.json
```

Этот адрес должен отдавать JSON без авторизации после публикации файла в `master`.
Для приватного репозитория нужен отдельный публичный адрес: телефоны пользователей
не имеют GitHub-доступа владельца проекта. Пока манифест недоступен, стартовая модель
скачивается по встроенному описанию; проверка обновлений показывает ошибку и сохраняет
установленную модель. Адрес можно переопределить при сборке:

```sh
bash ./gradlew :app:assembleRelease -PmodelManifestUrl=https://example.com/models/embedding-model.json
```

Для выпуска новой модели:

1. Разместить самостоятельный ONNX-файл по стабильному HTTPS-адресу.
2. Обновить `app/src/main/assets/models/embedding-model.json`: `version`, `displayName`,
   `url`, `sizeBytes`, `sha256` и контракт входа/выхода. Обновить сведения о лицензии,
   если меняется источник модели; текущие уведомления относятся к SigLIP 2.
3. Проверить модель на поддерживаемых устройствах и опубликовать манифест в `master`.
   Уже установленное приложение увидит его по кнопке проверки.
4. Пользователь нажимает «Обновить и повторить анализ». До завершения проверки файла
   остаётся активной старая модель; во время прохода анализа версия не меняется.

Поддерживаемый контракт (`schemaVersion: 1`): единственный float32-вход NCHW
`[1, 3, inputSize, inputSize]`, float32-выход `[1, dimensions]`, RGB с bilinear resize,
белым фоном под прозрачностью и нормализацией `(channel / 255 - mean) / std`.
Имена входа/выхода, размер изображения, размерность, `mean` и `std` берутся из манифеста.
Ограничения: `inputSize` 16–1024, `dimensions` 2–4096, файл не больше 512 МиБ.
`minAppVersion` проверяется по `versionCode`. Новые алгоритмы предобработки, внешние
файлы весов и операции, которых нет в установленном ONNX Runtime, требуют обновления
приложения или другого экспорта модели.

Текущая модель принимает RGB 224×224 и выдаёт `pooler_output` из 768 чисел.
Векторы квантуются в знаковые байты, по одному байту на измерение. Идентификатор
признаков вычисляется из SHA-256 весов, контракта обработки и версии квантования.
Замена весов или параметров автоматически делает старые признаки несовместимыми,
даже если издатель повторно использовал строку `version`. Признаки доступных фото
пересчитываются; решения пользователя сохраняются. Старые признаки уже удалённых
фото не участвуют в рекомендациях новой модели.

### Локальная модель для тестов

```sh
python3 tools/fetch_embedding_model.py
```

Скрипт читает тот же манифест и сохраняет модель в `build/model-fixtures/`.
Эта папка подключена только к `androidTest.assets`, поэтому реальная модель попадает
в тестовый APK, но не в приложение. Unit-тесты и сборка приложения обходятся без неё.
Тесты `PhotoEmbeddingExtractorTest` и `AnalysisLifecycleTest` требуют этот файл;
они устанавливают его через тот же код проверки и хранения, используя локальный
транспорт вместо сети.

Работа нейросети и ранжирование выполняются вне UI-потока. В проходе работает
один анализатор с двумя вычислительными потоками. Модель закрывается при остановке.
Храним до 2000 примеров каждого состояния; для расчёта берём до 128 последних
оставленных и 128 помеченных/удалённых. Для большой истории короткая проекция
выбирает 48 кандидатов, затем полный вектор определяет до 8 соседей.

Минимальное сходство 0.70, минимум 3 подходящих примера и сглаживание 3 —
консервативные стартовые эвристики. Результат — приоритет, не вероятность удаления.
Возраст только ослабляет перенос решения между свежими и давними снимками;
неизвестная дата съёмки не подменяется датой импорта.

## Проверка качества

Автотесты проверяют прерванную/повреждённую загрузку, несовместимую модель, откат,
загрузку сохранённой модели после перезапуска, контракт манифеста и интерфейс загрузки.
Также покрыты реальные вычисления модели, ранжирование, отмена и повтор
решений, удаление, очистку истории, миграцию БД и стабильность видимых карточек.
Они не измеряют полезность рекомендаций для людей.

Для настройки порогов нужна отдельная выборка реальных решений. Делить её
следует по времени и по группам похожих фото: кадры одной серии не должны попасть
одновременно в обучение и проверку. Сравнивать качество, качество с историей и
долю удалённых среди первых K предложений. Учитывать долю оставленных/восстановленных,
время анализа, расход памяти и разнообразие новых сюжетов. Тестовая галерея из
`seed_emulator_gallery.py` не заменяет такую выборку.
